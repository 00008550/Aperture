## 002-P4 — Deals + deal lines: aggregate, creation, scoped grid; account-reassignment re-stamps all children (edge 8)

Plan: [`002-sales-accounts-contacts-deals.md`](../002-sales-accounts-contacts-deals.md) · Roadmap: ARCHITECTURE.md §13 item 002.

### What this portion does

- **Deal aggregate (`sales.deals`).** A deal is created in stage `new`, owned by one agent, with its tenant and all five scope columns (`owner_user_id/team_id/region_id/account_id` + `tenant_id`) inherited from its parent account at write time — never from the request body. The one-account rule and the visibility check are the same load: the parent account is fetched through `WhereInScope`, so opening a deal against an account the caller cannot see (out-of-scope or cross-tenant) fails closed as not-found. `xmin` optimistic-concurrency token on the deal.
- **Deal lines (`sales.deal_lines`), a child of the aggregate.** Price + quantity + price-list version; created only through `Deal.AddLine`, loaded and saved with the deal. Lines are `ITenantOwned` (tenant global filter) but deliberately **not** `IScopedResource`: they carry no denormalised scope columns, RLS is not enabled on `deal_lines`, and they are never read through the reader-role grid on their own — only as part of the aggregate, whose parent deal is itself scope-filtered.
- **Endpoints** (all policied): `POST /api/deals` and `POST /api/deals/{id}/lines` on `deals.write`; `GET /api/deals` (keyset-paginated grid via `ScopedConnection`) and `GET /api/deals/{id}` on `deals.read`. Turns `deals.write` from declared→enforced.
- **`ScopeRlsPolicy.Enable("sales","deals")`** in the migration; the reader role's RLS re-asserts tenant + scope below the grid SQL. `deal_lines` gets no RLS by design (documented in the migration).
- **Edge 8 — account reassignment re-stamps ALL children (contacts AND deals), atomically.** `AccountService.UpdateAsync` now loads the account's contacts and deals **by `account_id` within the tenant global filter but NOT scope-narrowed** (so no child is missed even when the acting user cannot see some of them), calls `Reinherit(account)` on each to re-stamp `owner_user_id/team_id/region_id`, and commits them in the **same `SaveChangesAsync`** as the account edit — one transaction, all-or-nothing. `tenant_id` and `account_id` are never mutated.
- **EF change-tracking fix.** Add-line uses `_db.DealLines.Add(line)` to pin `Added` state: a client-keyed line appended to a tracked aggregate was otherwise inferred as an UPDATE (0 rows → concurrency exception). Matches the account/contact create pattern.
