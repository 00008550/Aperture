## 002-P5: Deal state machine — table-driven transitions + rules 1, 2, 4

Roadmap: plan **002 — Sales: accounts, contacts, deals** (`docs/plans/002-sales-accounts-contacts-deals.md`), portion **P5** (lines 229–233), closing edges 9/10/11/12/15.

### What this portion does
- **One place the lifecycle is written down.** `Sales/Domain/DealStateMachine.cs` holds the legal `(from,to)` edge table with a per-edge guard: `new -> qualified -> quoted -> negotiation -> won|lost`. `won`/`lost` appear only as targets, so they are terminal by construction. Any pair not in the table is `IllegalTransition`. The machine only decides; it never mutates a deal.
- **The rule guards.** Rule 1 — `won` requires >=1 line with both a price and a quantity. Rule 2 — `quoted` requires a price-list version, which `Deal.Transition` then freezes onto the deal and every line so a later price change cannot alter an outstanding quote. Rule 4 — `lost` requires a reason code, persisted on the row. (Rule 3 / discount approval is P6, out of scope here.)
- **`POST /api/deals/{id}/transition`** under `deals.write`. The deal is loaded and saved through the caller's scope (`WhereInScope`), so a deal the caller cannot see is a non-leaking 404. Illegal/terminal edges and the three rule-guard failures are `422`; optimistic-concurrency loss is `409` with the current persisted state (edge 15), guarded by both an up-front `ExpectedVersion` (`xmin`) pre-check and the EF concurrency token at commit.
- **One audit row per transition attempt** via `IAuditTrail`, recording actor, from->to and the reason (or `rejected: <outcome>` for a guard/illegal rejection — edge 12). Not-found and conflict are not recorded.

### Audit transactionality — reviewer note
The plan's design rationale (lines 69, 137) describes the audit row as landing "in the same unit of work" as the mutation. That holds for Access-module mutations, but the audit store lives in Access's schema/context and Sales may reference only SharedKernel and Contracts (CLAUDE.md section 1). A single transaction spanning both DbContexts needs shared-transaction/outbox infra this plan defers. The builder therefore writes the audit row host-side in the endpoint (the same seam that audits denials), reliably but outside the Sales write's transaction, documented inline. This satisfies P5's Done-when ("audited") and its Tests ("audit row written with from->to and reason") without a boundary violation. The "same unit of work" wording in the plan's prose is a surveyor reconciliation item, not a code defect.
