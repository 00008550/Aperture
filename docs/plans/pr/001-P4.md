# 001-P4 — Scope → SQL predicate translation

Plan: [`docs/plans/001-authorization-spine.md`](../001-authorization-spine.md), portion **P4**.
Roadmap: `ARCHITECTURE.md` §13 item 001.

## What this portion does

A `DataScopeSet` now becomes an `Expression<Func<T, bool>>` that a query provider turns into a
`WHERE` clause, so the database never hands the application rows the principal may not see.

- `src/Aperture.SharedKernel/Authorization/ScopeQuerying.cs` — `ToPredicate<T>()` and
  `WhereInScope<T>(IQueryable<T>)`. The predicate is *tenant equality* `AND` the *union* of the
  grants. `WhereInScope` composes, so ordering, paging and projection still run in the database
  on top of the scoped set.
- `src/Aperture.SharedKernel/Authorization/ScopeRowExpressions.cs` — binds the `IScopedResource`
  members on the **concrete** entity type, not the interface (an interface member access compiles
  and then filters on the client, which is the exact failure this portion exists to rule out), and
  wraps scope values so the provider emits SQL parameters rather than inlined literals.
- `DataScope` gains an abstract `ToPredicateBody`, with one override per scope kind and **no
  default branch** — a new scope kind fails to compile until it says how it filters, instead of
  falling through to "match everything".

Fail-open properties, each with a test:

- **Empty set matches nothing.** `DataScopeSet.None` compiles to `row => false`, produced before
  the row members are bound, so no widening branch can be added later. Postgres receives
  `WHERE FALSE`.
- **The tenant conjunct is not droppable.** It is `AndAlso`-ed outside the union, so not even
  `AllTenant` can reach past it; `AllTenant` alone emits `WHERE t.tenant_id = @p`, never an
  unfiltered scan.
- **Absent data narrows.** `team_id`/`region_id`/`account_id` are compared with plain equality
  against a parameter, so a `NULL` column is unknown and therefore not a match.
- **Nothing client-evaluates.** A type whose scope members are explicit interface implementations
  throws at predicate-build time rather than silently filtering in memory.

84 backend tests, all green.

The SQL half asserts the **generated `WHERE` clause** against real Npgsql SQL, not result counts —
a count assertion passes just as well for an in-memory filter over the whole table, which is the
regression the plan names. Examples asserted verbatim:
`r.tenant_id = @Value AND r.owner_user_id = @Value1`, `r.tenant_id = @Value` for `AllTenant`, and
`FALSE` for the empty set. The union test additionally allows either disjunct order, because the
set is unordered. A `ScopedRow` probe table lives in its own `scope_probe` schema **inside the
test project**, deliberately without a global query filter, so a fail-open translation cannot be
masked by EF's tenant filter.

`scripts/measure.sh schema` reports 9 tables in `access` — the probe table is excluded, which is
the one line of tooling this portion changed.

## Out of scope

No production query uses `WhereInScope` yet — no module has a list endpoint to apply it to. No
endpoint, no schema change, no migration, no Dapper path (raw SQL still has to pass `tenant_id`
explicitly; nothing here changes that). Postgres RLS remains deferred per the plan's design table.
