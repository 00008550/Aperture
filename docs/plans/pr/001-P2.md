# 001-P2: Access module schema, tenant query-filter convention

Plan: `docs/plans/001-authorization-spine.md` · Roadmap: `ARCHITECTURE.md` §13 item 001

## What this portion does

Nine tables in the `access` schema — `tenants`, `users`, `memberships`, `roles`,
`role_permissions`, `membership_roles`, `scope_grants`, `teams`, `regions` — and the convention
that keeps them tenant-isolated.

**Identity is global, authorization is per membership.** One person who works with two of the
platform's regional companies is one `users` row with two `memberships`, not two accounts sharing a
password. Duplicating identity per tenant is what makes "reset my password" ambiguous and lets an
offboarding miss a copy. The cost is stated where it lands: `users` is the one table a query must
never tenant-filter, and it is reachable only through a membership lookup.

**The tenant filter is applied by convention, not per configuration.** `OnModelCreating` walks the
model and filters every `ITenantOwned` entity. A filter that each configuration must remember to add
is one that will eventually be forgotten on the table where it matters — and the omission is
invisible in review, because the query still works, it just returns too much.

**Permissions and scopes are rows, not numbered columns.** The legacy shape this replaces is
`Right1..Right20`: a hard ceiling customers hit, where granting the 21st thing is a migration.
Adding one here is an insert.

**`ScopeGrant` is the persisted form of P1's `DataScope`** and projects back onto it through an
exhaustive switch over a closed hierarchy — adding a scope kind without handling it fails to
compile rather than silently granting nothing. Its shape invariant (a `Team` grant has a team; a
`Self` grant does not) is enforced by the constructor *and* a check constraint: the constructor
protects the application path, the constraint protects every other one.

The 15 Access tests run against **real PostgreSQL via Testcontainers with the real migration
applied** — not SQLite, not the in-memory provider. A check constraint, a unique index and the
migration itself either do not exist or behave differently on a substitute, so a test against one
would prove the wrong thing. `MigrateAsync`, never `EnsureCreated`: a suite that uses
`EnsureCreated` never runs the migrations it is meant to protect, and the first broken migration
reaches production green.

Notable tests:

| Test | Why it exists |
|---|---|
| `Every_tenant_owned_entity_has_a_query_filter` | The load-bearing convention test. Runs without a database, in milliseconds, on every build. |
| `Every_entity_carrying_a_tenant_id_declares_ITenantOwned` | The inverse, and the one that catches real mistakes — an entity with a `TenantId` but no marker is skipped by the convention and readable across tenants. |
| `The_convention_actually_covered_every_tenant_owned_type_in_the_assembly` | Guards the guard: an entity absent from the model passes the first test vacuously. |
| `The_tenant_filter_is_applied_in_SQL_not_in_memory` | A row-count assertion passes equally well against an in-memory filter that already pulled every tenant's rows over the wire. |
| `A_read_in_one_tenant_cannot_see_another_tenants_rows` | Including fetch-by-primary-key, the path most likely to skip a filter. |
| `A_scope_grant_that_needs_a_target_is_rejected_by_the_database` | Inserts raw SQL deliberately, bypassing the constructor — the constraint must hold for paths that are not this application. |
| `Contexts_sharing_one_options_instance_each_filter_by_their_own_tenant` | See finding 2. |

## Review findings and how they were resolved

**Finding 1 — a doc comment claimed a foreign key that does not exist.** `CONFIRMED`.
`Team` and `Region` said they existed so `scope_grants.target_id` had "a real foreign key to point
at". Checked against the live database: `scope_grants` carries only its primary key, the membership
FK and the check constraint. It *cannot* have one — the column is polymorphic. A maintainer
trusting that comment would assume referential integrity and skip validating a target.
→ Fixed in `e44dd11`: the comments now state the gap and its cost — deleting a team leaves grants
referencing nothing, which fail closed but are never cleaned up — and name 001-P4 as the owner.

**Finding 2 — load-bearing behaviour with no test.** `CONFIRMED`.
EF caches the model per options instance while the context is scoped, so the filter closes over the
*first* context ever built. It works only because the captured node is a property read that EF
re-evaluates per query, and because `ITenantContext` is a singleton over `AsyncLocal`. Register it
scoped, or capture `tenant.TenantId` as a value rather than a property, and every request after the
first filters by the first request's tenant — with no test failing.
→ Fixed in `e44dd11`: `TenantFilterModelCacheTests` asserts it, positively and negatively so it
cannot pass by the tenant simply being absent from the SQL.

**Finding 3 — the portion changed nine files outside its stated `Touches`.** `CONFIRMED`.
Several were consequential rather than creep, but an unamended `Touches` means the next reviewer
cannot tell which — and that distinction is the whole basis of scope review.
→ Fixed in `e44dd11`: the plan now records each one and why. The substantive ones:
`Directory.Packages.props` (this portion's own packages pulled EF 10.0.11 and 10.0.4 side by side —
MSB3277, an MSBuild warning that `TreatWarningsAsErrors` does not catch), and `scripts/measure.sh`
+ `measure_schema.awk` (the schema measurement only became wrong once a schema existed: it reported
one table per file, counted every `.Property` in the file as that table's columns, and counted
migration snapshots as tables).

## Found while building, fixed in place

The design-time factory and the runtime registration disagreed about the migrations history table:
`dotnet ef` wrote to the default `__EFMigrationsHistory` while the module expected
`access.__migrations`. A migration applied by the CLI would have been invisible to the application
and applied a second time on startup. Both now go through one `UseAccessNpgsql`, and
`The_migration_creates_the_access_schema_and_its_history_table` is the regression test.
