## 009-P3 — `ScopedConnection`: the only door to raw SQL

Plan: `docs/plans/009-raw-sql-scope-safety.md` (P3). Roadmap: ARCHITECTURE.md §13 — the raw-SQL
half of 001's authorization spine. Closes the gap left by `WhereInScope` (EF/`IQueryable` only).

### What this portion does

- Adds `Aperture.SharedKernel/Data/ScopedConnection.cs` — the single sanctioned wrapper over Dapper.
  A scoped read is issuable **only** by supplying a `DataScopeSet` and a `ScopeColumns`; no query
  overload omits either (`QueryAsync<T>` and `QuerySingleOrDefaultAsync<T>`).
- The wrapper **composes P2's fragment itself**: the caller marks where the predicate belongs with
  `ScopePlaceholder` (`/**scope**/`); the wrapper substitutes `({fragment})` and merges the
  fragment's bound scope parameters. A query missing the placeholder fails closed with
  `ArgumentException` at the call site.
- Scope parameters are added **after** the caller's own parameters, so a caller parameter cannot
  shadow the tenant/grant params — the scope value wins.
- Dapper lands in `Directory.Packages.props` (centrally pinned, `2.1.66`) and is referenced by
  **exactly one project** (`Aperture.SharedKernel`). The P1 architecture test is tightened to assert
  exactly-one-and-it-is-the-sanctioned-one.
- Observability: an `ActivitySource` span tagged with tenant id, alias, and per-kind scope
  **counts** — never scope values; and an `Information` log line when the scope set is empty
  ("user sees nothing" is one log line, not a debugging session).

### Amendment beyond stated Touches

`Microsoft.Extensions.Logging.Abstractions` (Abstractions only, centrally pinned) was added to the
package graph and the SharedKernel csproj. It is a genuine necessity: the Observability section
mandates the empty-scope `Information` line, which requires `ILogger<ScopedConnection>`. Correctly
scoped — Abstractions, not the full logging package.

### Known limitation (not a P3 defect — inherent to the plan's fragment model)

The wrapper validates only that `ScopePlaceholder` is **present**, not that it gates the outer rows.
A caller who writes the SQL adversarially or carelessly can still neutralise scope, e.g.
`WHERE 1=1 OR /**scope**/`, a `--`-commented placeholder, or a placeholder in a non-gating
subquery/`UNION` branch. This is the residual the plan accepted when it chose "produce a fragment;
let the developer write the query" and explicitly **rejected** owning the whole `SELECT`. Tightening
it further (e.g. RLS, or whole-statement wrapping) is a plan-level decision, not a P3 change. Worth a
follow-up note in the wrapper's XML guidance to state the placeholder must be a top-level AND-ed
conjunct. Separately, P2's fragment does not emit the `/* scope */` pg_stat_statements marker the
Observability section mentions — a P2 (already merged) concern, tracked for a later hardening pass.
