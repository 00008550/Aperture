# 001-P3: JWT authentication, permission policy provider, `GET /api/me`

Plan: `docs/plans/001-authorization-spine.md` · Roadmap: `ARCHITECTURE.md` §13 item 001

## What this portion does

The first authenticated request. A bearer token arrives, and by the time an endpoint runs the
request has a tenant, an identity, a set of permissions and a set of data scopes — all of them
resolved from the `access` schema P2 built.

**The token says who signed in. It does not say what they may do.** Every request resolves the
principal out of the database through `IAccessPrincipalResolver`: the tenant is active, the
membership is live, the user is active, and the permissions are whatever `access.role_permissions`
says right now. A revoked membership stops working on the next request rather than when the token
expires. The cost is one query per request, accepted deliberately — the plan defers caching until a
measured p95 asks for it, not a guess.

**The request principal is built from the resolved answer and nothing else.** Not filtered — built.
`ClaimsPrincipal.HasClaim` searches every identity on the principal, so a resolved identity
*appended* to the token's own would leave a token-supplied `perm` claim indistinguishable, at the
moment of the authorization decision, from a permission read out of the database. Constructing the
principal from scratch means a claim exists only because `BuildPrincipal` put it there, which closes
the next claim someone decides to trust as well as this one. (See finding 1.)

**A permission is a policy nobody registered.** `PermissionPolicyProvider` manufactures a policy per
permission on demand, so `RequirePermission("orders.confirm")` works without a hand-maintained list
that drifts from `Permissions.cs`. An undeclared permission still yields a policy — an unsatisfiable
one. Returning null would make ASP.NET report "policy not found", a 500 that invites the wrong fix;
an unsatisfiable requirement locks the endpoint, which is the fail-closed answer. A typo caught
earlier still throws at map time, because startup is the cheapest moment to find one.

**Failing closed is arranged so nobody has to write the deny.** `PermissionAuthorizationHandler` has
no else branch: a handler that does not call `Succeed` denies, so an undeclared permission, a
missing claim and a claim differing only in case all end in a denial without a line of code
expressing it. The fallback policy is `RequireAuthenticatedUser`, so a route someone maps without a
policy is closed in the window before anybody runs the architecture test.

**The tenant comes from the principal and from nowhere else.** `TenantScopeMiddleware` sets the
ambient tenant after authentication and before authorization. It is separate middleware because the
authentication handler's execution context does not flow forward — an `AsyncLocal` set there is gone
by the time an endpoint runs. A request with no principal gets no tenant, so anything tenant-scoped
it touches throws rather than defaulting.

**`GET /api/me` is authentication-only by design.** Gating it behind a permission would leave a user
with no grants unable to discover that they have none — and that empty state is exactly what the
console must render explicitly in P5 (DOMAIN.md §5.1).

**The host refuses to start without an issuer, audience and signing key.** No defaults:
`appsettings.json` supplies no `Authentication` section at all, because a default signing key in the
repository is a credential some deployment will keep. HS256 is pinned by `ValidAlgorithms`, which
closes `alg: none` and RS256/HS256 confusion together.

## Review findings and how they were resolved

**Finding 1 — a well-signed token could name its own permissions.** `CONFIRMED`, high.
`ResolvePrincipalAsync` appended the DB-resolved permissions as an extra `ClaimsIdentity`, and
`ClaimsPrincipal.HasClaim` searches every identity — so `perm` claims carried in the token satisfied
`RequirePermission` for grants the user did not hold, and revoking the role did not deny until the
token expired. Not exploitable without the signing key today, but P5 is the sign-in flow that mints
these tokens, and the obvious shortcut of embedding permissions so the console can render navigation
would have turned it into a live bypass with every test still green.

Fixed in `98b299f`: `BuildPrincipal` constructs the principal from the resolved `AccessPrincipal`
and assigns it to `context.Principal`, discarding the identity the token arrived with. A whitelist,
not a filter, so the next claim someone decides to trust is closed too. Verified by mutation:
restoring `AddIdentity` fails `A_permission_written_into_the_token_does_not_satisfy_RequirePermission`
(403 becomes 200) and **only** that test — the `/api/me` half passes against the broken code,
because `AccessPrincipal` was always DB-derived and the bypass lived solely on `context.User`.
Asserting at both levels is what made the test bite.

**Finding 2 — every authentication deny path was silent.** `CONFIRMED`, medium.
Five distinct refusals — malformed token, inactive tenant, no membership in the named tenant,
inactive user, invalid or expired token — collapsed into one indistinguishable 401. The
`context.Fail` reasons were discarded (JwtBearer logs handler exceptions, not a `Fail` result), and
nothing in the new code took an `ILogger`. Nobody could separate revocation from clock skew without
a debugger on a running host, and "one subject, many tenant ids" — a replayed token being probed
against other tenants — had no signal at all. Plan 001 committed this wiring to P3.

Fixed in `98b299f`: the resolver returns an `AccessPrincipalResolution` carrying an
`AccessDenialReason` (`TenantInactive`, `NoActiveMembership`, `UserInactive`; the enum starts at 1,
so a default-initialised reason is not a real one) and each refusal logs a source-generated
structured warning — 1001 malformed, 1002 not resolved, 1003 token rejected. The reason never
reaches the HTTP response: a 401 that explains itself tells an attacker which half of the guess was
right. Verified by mutation: collapsing `TenantInactive` into `NoActiveMembership` fails
`A_deactivated_tenant_logs_a_different_reason`.

Event 1003 goes beyond what the review asked for. JwtBearer logs validation failures at Information
and drops the reason, which left ordinary token failures as the one deny path with no warning-level
signal. It records the exception type only, never the message, which can carry token contents.

## Amended scope, and one judgement call

The portion touched more than its stated `Touches`; the plan records each addition and why. The
substantive ones: a new `Aperture.Api.Tests` project wired into `Aperture.slnx` (the API host had
none), and `scripts/measure.sh` — the route pattern is now any `Map<Something>("...")` rather than a
verb vocabulary that could not see `MapHealthChecks`, and the policy scan runs to the end of the
statement rather than a fixed six-line window that reported `/api/me` as unpoliced purely because
its handler was long. A gate that depends on formatting is a gate people learn to override.

**Reviewed and accepted:** `TokenClaimTrustTests.StartHostWithAGuardedRouteAsync` composes a
`TestHost` from the same three registration extensions as `Program.cs` and maps one guarded route,
because production maps no `RequirePermission` endpoint yet and a 403 test needs one. It duplicates
the middleware order, which is real drift risk — but the behaviour under test (whether a
token-supplied claim satisfies a permission requirement) is decided entirely inside shared
production code, exercised against a real JWT handler and a real database, and the mutation check
above confirms it bites. **Follow-up for P4/P5:** when the first real permission-gated endpoint
exists, point this test at the production host and delete the locally composed one.

## Out of scope, deliberately

No token-issuance endpoint — console sign-in is P5, and this portion validates tokens rather than
minting them. Symmetric HS256 only; asymmetric keys and SSO/OIDC federation are out of scope for the
whole plan. No permission caching (deferred until a measured p95 asks for it). No audit rows: 001-P6
owns the audit trail, and writing them here would be that portion done badly and early. No scope-to-SQL
translation — scopes are reported by `/api/me` and not yet applied to a query, which is P4.
